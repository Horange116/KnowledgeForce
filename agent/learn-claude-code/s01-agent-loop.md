# s01 Agent Loop 学习总结

## 本章主题

本章学习的是 Claude Code / Coding Agent 最核心的运行机制：Agent Loop。

Agent Loop 可以理解为一个循环：

```text
用户输入
→ LLM 根据上下文判断下一步
→ 如果需要工具，则发起 tool_use
→ Harness 执行工具
→ 工具结果回填到 messages
→ LLM 基于观察结果继续判断
→ 直到给出最终回答
```

这一章的重点不是某个具体工具，而是理解 Agent 的基本分工：

```text
The model decides. The harness executes.
```

也就是：

- 模型负责判断下一步要做什么；
- Harness 负责提供工具、执行工具、管理上下文和回填结果；
- 工具执行结果必须重新进入 messages，模型才能继续推理。

---

## 一、messages 里保存了什么

`messages` 保存的是 Agent 到目前为止的完整上下文记录，相当于 Agent 的工作记忆。

通常包括：

- 用户提出的问题；
- 模型的中间回复；
- 模型请求调用的工具；
- 工具真实执行后的结果；
- 模型基于工具结果继续生成的内容。

例如：

```text
User: 帮我看看当前目录有哪些文件
Assistant: 我需要调用 list_dir 工具
Tool Result: 当前目录有 README.md、main.py、requirements.txt
Assistant: 当前目录包含 README.md、main.py 和 requirements.txt
```

如果没有 `messages`，模型就不知道之前发生过什么；如果 `messages` 里没有工具结果，模型就不知道自己的动作产生了什么结果。

---

## 二、tool_use 是谁决定的

`tool_use` 是模型决定的，不是代码提前写死的。

传统程序通常是：

```text
if 条件 A:
    执行动作 B
```

而 Agent Loop 中，代码只是把工具列表、上下文和用户问题提供给模型，模型自己判断：

- 当前问题能不能直接回答；
- 是否需要读取文件；
- 是否需要执行命令；
- 是否需要搜索信息；
- 是否需要继续调用其他工具。

所以 Agent 的关键不是把流程完全写死，而是给模型一个可操作的环境，让模型在环境里逐步完成任务。

---

## 三、工具执行结果为什么要回填

模型本身并不会真的执行工具。模型只能发出工具调用请求，例如：

```text
read_file("main.py")
```

真正执行 `read_file` 的是外部 Harness。执行完成后，Harness 必须把结果作为新的消息放回 `messages`。

这样模型下一轮才能看到：

- 文件内容是什么；
- 命令有没有成功；
- 报错信息是什么；
- 下一步应该继续查什么；
- 是否可以生成最终答案。

因此，工具调用不是终点，而是 Agent 循环中的一次行动。工具结果回填后，模型才获得观察能力。

---

## 四、如果不回填会发生什么

如果工具结果不回填，Agent 会失去观察能力。

可能出现的问题包括：

- 模型不知道工具是否执行成功；
- 模型不知道读取到的文件内容；
- 模型不知道命令报错原因；
- 模型可能重复调用同一个工具；
- 模型可能开始猜测结果；
- 模型可能提前给出错误结论。

例如用户让 Agent 检查 `main.py` 的 bug，模型调用了 `read_file("main.py")`。如果读取结果没有回填，模型其实并没有看到代码内容，只能瞎猜。

所以完整 Agent 必须是：

```text
行动 → 观察 → 推理 → 再行动
```

而不是：

```text
行动 → 结束
```

---

## 五、从 Claude Code 迁移到企业流程 Agent

在 Claude Code 中，最小可用工具通常是 Bash、Read、Write、Edit 等，因为它面向的是代码环境。

但在企业流程 Agent 中，Bash 应该被替换或扩展为企业内部的业务工具和接口，例如：

- 查询数据库；
- 查询知识库；
- 解析 PDF、Word、Excel；
- 调用 OCR；
- 查询 CRM / ERP / OA 系统；
- 查询审批流；
- 调用内部 API；
- 创建工单；
- 发送邮件或通知；
- 生成结构化审查报告；
- 更新任务状态；
- 检查引用和证据来源。

所以两者结构可以类比为：

```text
Claude Code:
LLM + Bash + 文件系统 + Git + 权限控制

企业流程 Agent:
LLM + 企业 API + 数据库 + 文档系统 + 任务系统 + 权限系统
```

本质仍然一致：

```text
模型决定下一步
系统执行工具
工具结果回填
模型继续判断
```

## 六、本章建立的核心认知

本章最重要的收获是：Agent 不是一个更长的 Prompt，也不是简单的多轮聊天，而是一个由模型驱动的工具循环。

Agent Loop 的基本组成是：

1. `messages`：保存上下文和工作记忆；
2. `LLM`：根据上下文判断下一步；
3. `tools`：外部可执行能力；
4. `harness`：负责调用模型、执行工具、回填结果、控制循环；
5. `stop condition`：判断什么时候结束。

其中最关键的一句话是：

```text
模型负责决策，Harness 负责执行。
```

## 七、对后续学习的意义

后续章节中的 TodoWrite、Subagent、Skills、Context Compact、Task System、Background Tasks、多 Agent 协作，本质上都是在强化这个基础循环。

它们分别解决：

- Agent 如何规划任务；
- Agent 如何拆分复杂任务；
- Agent 如何按需加载知识；
- Agent 如何处理长上下文；
- Agent 如何把一次性对话变成可追踪任务；
- Agent 如何在多个角色之间协作；
- Agent 如何安全地执行更复杂的动作。

所以 s01 的 Agent Loop 是后面所有章节的基础。

## 八、本章需要记住的五个问题答案

### 1. messages 里保存了什么？

保存用户输入、模型回复、工具调用请求、工具执行结果和后续推理内容，是 Agent 的工作记忆。

### 2. tool_use 是谁决定的？

由模型根据当前上下文决定，代码只负责把工具能力暴露给模型并执行模型选择的工具。

### 3. 工具执行结果为什么要回填？

因为模型本身看不到外部工具的真实执行结果，只有回填到 messages 后，模型才能继续基于真实观察进行推理。

### 4. 如果不回填会发生什么？

Agent 会失去观察能力，可能重复调用工具、猜测结果、忽略错误或给出错误结论。

### 5. 迁移到企业流程时，Bash 应该替换成什么？

应该替换成企业业务工具和接口，例如数据库查询、知识库检索、文档解析、审批系统、工单系统、内部 API、报告生成和通知系统。
